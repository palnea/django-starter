# Internationalisation

[Back to docs index](../README.md)

The API serves English and Turkish. Every string a client can see must be
translatable, and there are tests that fail your build if one is not.

---

## Configuration

```python
LANGUAGE_CODE = "en-us"
LANGUAGES = [("en", "English"), ("tr", "Turkish")]
LOCALE_PATHS = [os.path.join(BASE_DIR, "locale")]
USE_I18N = True
```

`django.middleware.locale.LocaleMiddleware` is the last entry in `MIDDLEWARE`.
Catalogues live in `locale/en/LC_MESSAGES/` and `locale/tr/LC_MESSAGES/`, as a
`.po` source and a compiled `.mo`. The `.po` files are committed. The `.mo` files
are gitignored and rebuilt by `compilemessages`, which is why CI and `bin/setup`
both run it.

---

## Which language a request gets

Resolved by `GlobalContext.language_code`, in this order:

1. A `language` or `locale_code` query parameter, if it is a valid `LocaleCode`.
2. The `locale_code` claim on the JWT, meaning the language the user chose.
3. `en`.

So a client can override per request, and otherwise gets the language stored on
their account. See [logging-and-context.md](logging-and-context.md).

Do not confuse this with the `Locale` and `Translation` models in `common`. Those
are a database-backed content translation layer for things like product titles,
and are separate from the `gettext` catalogues that translate the application's
own strings. See [../apps/common.md](../apps/common.md).

## The normal case

Wrap the string and move on:

```python
from django.utils.translation import gettext_lazy as _

raise CustomException.business_logic_error(
    title=_("Already Inactive"),
    detail=_("User is already deactivated."),
)
```

Use `gettext_lazy as _` everywhere: models, serializers, services, views,
exception factories. Lazy matters, because a module-level string evaluated
eagerly would bake in whichever language happened to be active at import time.

## The exception handler mapper is a special case

`common/exception_handling/exception_handler_mapper.py` does **not** use
`gettext_lazy` in its handlers. It uses plain strings, and translates them at
response time through `translate_message()`, which calls `gettext`.

That means `makemessages` cannot see them. So the file carries an explicit block
of markers near the top whose only job is to be discovered by `makemessages`:

```python
# Mark strings for translation - these will be picked up by makemessages
# but we'll translate them dynamically in the exception handlers
_("Already exist!")
_("Integrity Error!")
_("Content not found!")
...
```

### Adding a handler

Three steps, in order. Skipping step two fails the build.

**1. Add the handler.**

```python
EXCEPTION_HANDLER_MAPPER = {
    YourNewException: lambda x: ExceptionHandlingParameters(
        "Your error message!",       # plain string, not gettext_lazy
        status.HTTP_400_BAD_REQUEST,
        ErrorCode.YOUR_ERROR_CODE,
        "Your response message!",    # plain string, also needs marking
    ),
}
```

**2. Mark every new string** in the marker block at the top of the same file:

```python
_("Your error message!")
_("Your response message!")
```

Both the `error_msg` and the `response_message` need a marker. The strings must
match character for character, punctuation included.

**3. Regenerate and translate.**

```bash
python manage.py makemessages --all
# edit locale/tr/LC_MESSAGES/django.po and fill in the Turkish
python manage.py compilemessages
```

## The tests that enforce this

`custom_test/test_exception_translations.py` runs as part of the normal suite and
as a pre-commit hook. It checks:

| Test | Fails when |
|---|---|
| `test_all_handler_strings_are_marked_for_translation` | A handler string has no marker in the marker block. |
| `test_marked_strings_have_translations_in_all_languages` | A marked string has no entry in some language's `.po`. |
| `test_no_orphaned_translation_markers` | A marker exists for a string no handler uses any more. |
| `test_exception_handler_translations` | A handler in `EXCEPTION_HANDLER_MAPPER` does not translate correctly. |
| `test_api_exception_handler_translations` | The same, for `API_EXCEPTION_HANDLER_MAPPER`. |
| `test_exception_handler_mapper_structure_compliance` | A mapper entry has the wrong shape. |

The orphaned-marker test is worth calling out. If you delete or reword a handler
string, delete or reword its marker too, or the build fails on the leftover.

Run the same checks directly:

```bash
bin/check-translations
```

That script runs the three key tests and then `makemessages --all --dry-run`, so
it also catches unmarked strings you have not regenerated yet. `bin/setup`
installs it as a pre-commit hook.

## Commands

```bash
python manage.py makemessages -l tr          # update Turkish only
python manage.py makemessages --all          # update every language
python manage.py compilemessages             # build the .mo files
python manage.py makemessages --all --dry-run
```

`makemessages` needs GNU gettext installed. CI installs it explicitly with
`apt-get install -y gettext`.

## Rules

- Wrap every user-facing string in `gettext_lazy as _`, with the mapper file as
  the single documented exception.
- Never translate log messages. Logs are for operators and should stay in
  English so they aggregate cleanly.
- Never translate error *codes*. `ERR_NOT_FOUND_ERROR` and `invalid_email` are
  machine-readable contract, not display text. See [errors.md](errors.md).
- Commit the `.po` files. Do not commit `.mo`, which is gitignored build output.
- If you add a language, add it to `LANGUAGES`, run `makemessages` for it, and
  expect `test_marked_strings_have_translations_in_all_languages` to demand a
  complete catalogue.
